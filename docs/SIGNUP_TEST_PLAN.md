# Signup feature test plan

**Stage:** 2 plan with Stage 7 execution status. **Status:** approved and partially implemented through 2026-09-23. The [Stage 1 feature brief](SIGNUP_FEATURE_BRIEF.md) and subsequent gated stages were approved by the requesting user. The inventory below preserves stable IDs and distinguishes implemented coverage from deferred work. It follows the [roadmap](TEST_ROADMAP.md) and [agent workflow](AGENT_TEST_WORKFLOW.md).

## Basis and boundaries

The QA [English](https://app.qa.nesto.ca/signup) and [French](https://app.qa.nesto.ca/fr/signup) pages are the current-behavior source. Live evidence now covers the complete visible form, language switching, consent, selected negative validation, and an automated accessibility baseline across three browser engines and both locales. Bounded account investigation observed `POST /api/accounts` return HTTP 201 with submitted non-secret account information and a non-empty identifier. The final ordinary confirmation reached `/getaquote` but stopped at the privacy guard because a sensitive-shaped optional response field was populated.

The approver permits QA account creation under a 20-attempt lifetime cap with persistent synthetic accounts and environment-owner cleanup. Ten attempts are consumed. The local ignored ledger is disabled after the final privacy stop. Production remains disabled. Mailbox receipt integration and active security probes are outside this first pass.

**Classification axes:** type (`ui`, `api`, `accessibility`, `readability`, `performance`); purpose (`smoke`, `regression`, `uat`); environment (`self-contained`, `staging`, `production`). Browser, locale, and data profile are run metadata. These are proposed classifications, not implemented tags. `P0` protects the critical path, `P1` covers common failures and inclusive use, and `P2` is deferred depth. Do not count a proposed case as live coverage.

## First delivery sequence

1. **Read-only baseline:** SGN-001, SGN-002, and SGN-009. Inventory the full form, validate language switching, and record accessibility violations with severity. SGN-004 keeps synthetic data parsing sound. Deliver a bounded static security review of this test repository and browser-observable signup controls, with a safe follow-up checklist. Application source is unavailable. Do not enforce a no-regression accessibility gate until the human reviews the baseline.
2. **One controlled account:** SGN-006 after the account lifecycle, response-redaction, and environment capability are approved. Begin in one browser and locale. The test observes the browser-triggered creation response; a direct API write test is a later decision.
3. **Focused negatives:** SGN-005, SGN-014, and SGN-015 after an agent documents actual QA UI responses and the same lifecycle covers their submissions. SGN-016 adds a few named edge cases from a file. Keep the first data set small. Reserve account budget before each submission that could create an account, even when validation is expected to reject it.

This sequence is the proposed narrow scope. SGN-003 and SGN-017 are read-only supporting checks on keyboard access and consent; they may be authored with the baseline if they add a distinct outcome. Do not multiply account creation across every browser/locale project merely because those projects exist.

## Basic checks and the appropriate test level

The following basic checks remain part of the overall signup quality strategy, but their exhaustive permutations should live close to the validation or mapping code in the application repository. Fast unit or component tests can cover them precisely without browser timing, selectors, persistent accounts, or repeated QA submissions. This test framework does not currently contain the application source, so these are recommendations for the owning development team rather than coverage claims.

| Basic behavior                                                                                                             | Primary test level                                                                                         | Browser coverage retained here                                                                                                                                                        |
| -------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Required-field rules for name, phone, province, email, password, and confirmation, plus the consent required/optional rule | Unit tests for the validation schema; component tests where the error presentation depends on field state  | One empty-form or representative required-field check confirms that validation is connected to visible, accessible feedback. Do not repeat every field permutation in Playwright.     |
| Email trimming, case handling, format parsing, and minimum/maximum boundaries                                              | Unit tests for normalization and validation functions, using a table of valid and invalid values           | One malformed value and one boundary example confirm browser wiring. Duplicate-account behavior stays at service/API and one UI journey because it depends on persisted server state. |
| Password length, character rules, confirmation matching, and boundary values                                               | Unit tests for password policy and confirmation comparison; component tests for guidance and error display | One policy failure and one mismatch confirm the visible behavior. Do not send a full password permutation matrix through QA.                                                          |
| Name and phone accepted-character rules, length limits, country-code mapping, and province-option mapping                  | Unit tests for validators and mapping functions                                                            | A small risk-based sample confirms controls serialize the selected values correctly. Locale and accessibility behavior remain browser concerns.                                       |
| Consent defaults, boolean serialization, and required/optional rule                                                        | Unit tests for form-state and request mapping; component test for control behavior                         | SGN-017 checks the visible control and SGN-006 checks one approved submitted state.                                                                                                   |
| Request construction, omission of confirmation, and safe mapping of submitted fields to the account-creation payload       | Unit tests for the request mapper plus API contract tests at the service boundary                          | SGN-006 observes one browser-triggered 201 response and compares only approved, non-secret fields.                                                                                    |

The browser suite should prove that the assembled user journey, localization, accessibility, controls, and backend connection work together. It should sample rule families rather than reproduce the full validator truth table. If the application repository lacks the recommended lower-level coverage, record that gap with its owning team; do not silently expand this UI suite into a substitute unless a human approves the additional cost and account risk.

## Data, execution, and implementation design

- **Account lifecycle proposal for human review:** at most two potentially account-creating submissions in the initial campaign, across all runs and retries, with no parallel submissions. Reserve one slot in a local Git-ignored ledger **before** each possible write, including duplicates and invalid-input submissions. Record the synthetic identity, attempt time, outcome, account ID if safely returned, accountable owner, and retention review date; record no passwords or tokens. An ambiguous or failed attempt holds its slot until the owner verifies account state through an approved method and reconciles the ledger. A retry requires another available slot; stop when the cap is reached or account state is uncertain. This may limit the first run to one positive case and one contingency; expand the budget only after human review. The approver has allowed capped persistence; this numeric attempt cap and details are **proposed**, not yet approved. No cleanup endpoint exists.
- **Data file:** keep committed examples synthetic under `test-data/scenarios/self-contained/`. A staging profile and its ledger remain Git-ignored. Extend the typed JSON parser to reject malformed values, duplicate IDs, and unknown case kinds before execution. Do not use real customer data or public inboxes.
- **Secret-bearing artifacts:** existing failure traces, videos, screenshots, and browser diagnostics may expose typed credentials or response bodies. Before SGN-006 or any write-capable negative case, design and verify redaction or disable unsafe capture for those cases. Save only sanitized evidence; never attach a raw 201 body when it may contain secrets.
- **Page objects and locators:** keep `LiveSignupPage` focused on form controls and deterministic navigation. Use a focused workflow only if the approved journey branches or crosses pages. Prefer unique role/label locators, then stable attributes, scoped relationships, text, and structural CSS/XPath last. Use named ordered `LocatorResolver` candidates only when needed; reject ambiguous visible matches and annotate the winning strategy. Avoid `.or()` as a purported priority fallback.
- **Locale/browser sampling:** author read-only checks in Chromium EN/FR, then verify P0 read-only behavior in Firefox/WebKit EN/FR; Edge remains opt-in. Start the write-capable positive in one approved browser/locale, and expand only when the account budget and risk justify it. WebKit is Safari-engine coverage, not branded Safari. Production is never selected.

## Reporting, triage, and measurement

For each future execution, preserve run ID, commit/branch, environment, case ID, browser, locale, data profile, retry, duration, and sanitized artifact links. The roadmap's machine-readable reporter and tag contract are not implemented yet. Keep current HTML/list and failure-only artifact behavior for read-only tests; review privacy controls before write-capable runs.

Group browser/locale repetitions into reviewed failure clusters. Keep `product-bug`, `automation-bug`, `test-data`, `environment`, `expected-change`, `no-defect`, and `untriaged` distinct, with owner, decision date, evidence, and issue link. A retry pass does not erase the first failure. For ROI, start with approved-requirement coverage, executed cases, unique confirmed bugs, actionable/false-alarm cluster rates, flake candidates, and triage time as defined in the [roadmap](TEST_ROADMAP.md). Do not call a failed execution a bug caught or claim dollar savings without cost evidence.
